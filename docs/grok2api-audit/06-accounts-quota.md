# 账号轮换 / 配额 / 限流对比

对比范围：Orchids-2api（以下简称 A）Grok 通道的账号选择/轮换、配额记账与门控、限流分类、冷却、重试/质量探测、失败分类与通道摘除，对 chenyme/grok2api（以下简称 B，HEAD `906b9493`，B 路径相对 `backend/`）。
A 的移植基线是 `44a390b8`（`internal/grok/grok2api_sse.go:1`、`internal/grok/grok2api_streamidle.go:1`、`internal/grok/grok2api_streamidle_test.go:1` 标注 "Derived from chenyme/grok2api, commit 44a390b890e7a3e0dd209b95b8c29a9f2b1be8dd"），距 HEAD 19 个提交。经 `git log 44a390b8..HEAD` 核对，本领域内**只有 `quality_retry.go` / `quality_retry_scan.go` 被 7f3f3d3c 改过**，因此"漂移"仅出现在质量重试分类器上，其余差异都是移植时的取舍而非上游变更。

## 结论摘要

- **A 没有质量闸门（quality hold / quality probe）整条子系统**：B 的 `quality_retry.go` + `quality_probe.go` + `quality_retry_scan.go` 在 A 无任何对应实现；A 的唯一重试触发条件是"上游返回错误"，所以上游用 encrypted-thinking 占位后一次性 dump 正文、或 `reasoning_tokens=0` 的 128k 状态循环，A 一律当 200 正常结果交付，账号也不会因此被降权。
- **"账号坏了要摘多久"这个问题 A 与 B 系统性不同**：A 是"短冷却 + 自动回池"（401→5 分钟、403→10 分钟、429→1 分钟），B 是"永久摘除等人工"（`AuthStatus=reauthRequired` 直接不进候选）或"模型级隔离 + 指数冷却"（`cooldownBase=30s` 倍增到 `cooldownMax=30min`）。A 会把上游已封禁/已拒绝凭据的账号每 5–10 分钟放回池子。
- **A 把上游 `Retry-After`/`resets in:` 无上限地写进 `QuotaResetAt`**（`grok "resets in: 2h"` → 该号停用 2 小时），B 有 `boundUpstreamRetryAfter` 用 `cooldownMax` 截断；同时 A 内部两套冷却对同一个 429 给出不同答案（池 1 小时 vs 调度器 `AccountHeld` 1 分钟）。
- **A 把"按模型"的免费额度耗尽当成整号 24 小时封停**（匹配子串 `used all the included free usage`，不含 B 的 `for model` 区分），B 用 `subscription:free-usage-exhausted` 才整号、`used all the included free usage for model` 只封该模型。
- **A 的付费额度快照完全不参与路由**：`GrokBilling` / `UsageCurrent` 只用于后台展示与 Free 推断，选号只看 `StatusCode`；B 用 `Billing.IsExhausted(MinimumRemaining)` + 本地消耗增量门控，并按账期结束时间探测恢复。
- **选号排序 A 只有 `conns/weight` + 随机平局**：没有 `priority`、没有 `lastSelectedAt` 轮转、没有 quota/billing 新鲜度；B 是 11 级比较器的候选堆 + 分段（segmented）窗口轮转。
- 请求预算相差两个数量级：A 换号上限默认 **5**（硬上限 20），B `MaxAttempts` 默认 **999**（上限 65535，`-1` 表示无限）。
- 其余 P2/P3：5xx 软失败不写状态、分层池顺序逐池全量扫描、刷新调度 30 分钟/每轮 5 个 vs DB 到期/提前 3 分钟/批 100、永久失效凭据无收敛、订阅等级推断算法与阈值不同、无本地额度消耗计数、会话粘滞无解绑口。
